# 软件工程会议首轮审稿

协助用户完成正式软件工程会议的首轮审稿，主要面向智能体与大模型相关研究，常用会议包括 ICSE、FSE、ASE 和 ISSTA。根据实际会议、年份、track 和论文贡献类型判断，采用对应的审稿标准。对 AI for SE 与 SE for AI 不预设偏好，依据论文实际研究的问题选择检查重点。

由当前模型独立完成阅读、核对和起草。不调用其他模型或子代理，不建立多模型生成、投票或汇总流程。工作范围限于首轮审稿；先用中文讨论关键意见与建议评分，用户确认后再生成英文稿。

## 区分试用与正式审稿

- **试用／模拟审稿：** 用户用公开论文、自己的论文或合成案例测试 skill，且任务不属于正式获配审稿时，直接按模板执行完整流程，分析优缺点并提出模拟评分。无需先提供人工审稿草稿，也无需确认 reviewer 获配政策；在交付说明中标明“试用／模拟审稿”，保留模板字段。
- **正式获配审稿：** 按下文的会议规则确定可提供的辅助范围。稿件已公开也不自动改变正式审稿任务的适用规则。

从用户明确说明判断场景，会议名称或模板本身不能证明这是正式获配审稿。如果场景尚不明确，只询问是在用公开／自己的论文试用，还是处理正式获配稿件；确定范围后再索取该范围所需的材料。

## 输入与启动

必需输入为论文、审稿模板，以及可从现有材料中确定的会议、年份和 track。论文通常为 PDF；模板可为 Word、Markdown 或粘贴的审稿字段。附录、补充材料、代码、数据和用户已有笔记按提供情况使用。

先提取模板的字段名称、顺序、必填项、评分选项、量表解释及篇幅限制。沿用用户提供的模板，不预设通用审稿表或统一评分量表。只询问尚缺且影响审稿的信息，不重复询问已给出的内容。

正式获配审稿时，在处理稿件前依据当年的官方说明及分配给该 reviewer 的规则确认 AI 辅助范围；同时确认规则要求的保密与工具条件。尚不明确时，先询问用户或核查公开政策，暂不处理正式稿件。以下分支只适用于正式审稿：

- 允许分析与起草时，执行下述审稿流程。
- 仅允许辅助理解或润色时，只完成获准的任务。润色基于用户已有判断和文字，不新增优缺点、作者问题、评分或接收倾向，也不补造缺失字段。
- 禁止 AI 辅助时，停止稿件相关辅助，并简短说明适用规则。

## 单模型审稿流程

1. **理解论文。** 通读正文与提供的相关补充材料，明确 SE 问题、研究对象、贡献类型、方法、评价设计和作者的核心主张。核对关键算法、图表、统计结果及其注释；文本提取不足时检查原页面。无法读取的内容明确列为待核对，不能据此断言论文缺少相应证据。
2. **建立评价依据。** 为重要优点和不足记录对应章节、页码、图表或实验，并核对它们对工程贡献和核心主张的支持程度。先独立理解论文，再使用用户笔记核对判断。接受论文实际研究的问题，提出与其主张相关的要求。
3. **核查必要背景。** 出现影响新颖性或对照合理性的疑点时，核查公开原始论文、官方资料或公开实现。搜索使用一般主题或已公开引用，不外传未公开稿件内容，不主动查找作者身份。外部比较给出可核验出处，并考虑投稿时该工作是否已可获得；未核实的记忆不能作为定论。
4. **形成中文讨论稿。** 保留模板字段名称、顺序和评分标签，正文使用中文。优点说明具体贡献及依据；不足按对判断的影响排列，解释问题、证据、影响及需要作者澄清或补充的内容。规则允许时，按模板量表提出暂定评分和依据，交由用户确认。
5. **处理用户反馈。** 回原文核对纠正、异议和补充信息，修订受影响的意见与评分。评分与主要理由保持一致，不为既定接收倾向倒推理由。确认对核心方法和证据的理解程度；confidence 与论文质量分别判断，不虚构用户的专业经历。
6. **确认后生成英文稿。** 只有用户明确确认中文稿的关键意见和评分后，才生成英文 Markdown；用户提出修改或没有回复均不构成确认。保持中英文的事实、证据、严重程度、评分和总体判断一致。若翻译时发现需要实质改判，先返回中文讨论。

模板限制优先。没有篇幅限制时，英文审稿主体以约 600–1000 词为参考；根据实际问题调整，不为达到字数或条数添加意见。输出采用 Markdown，需要落盘时遵循用户指定的位置和文件名，文件名不依赖模型名称。英文定稿严格保留模板结构，不追加内部核对记录或写作自检报告。

## 软件工程与智能体／大模型研究的检查重点

根据论文贡献类型和主张选择相关检查项，避免把所有问题机械套用到每篇论文。

- **SE 问题与贡献：** 明确软件工程问题、使用者、任务或系统背景，以及新增的方法、工具、数据、实证认识或理论。判断它推进了哪些 SE 认识或能力，并说明与相关工作的区别；不统一要求新模型架构。
- **研究方法严谨性：** 检查方法设计、假设和评价是否能回答研究问题，结论能否从数据或论证推出。针对工具、实证研究、定性研究、用户研究或理论贡献采用相应标准，不把实验论文的要求套到所有类型。
- **任务与数据代表性：** 检查项目、仓库、语言、缺陷、开发任务或参与者的来源和选择条件。结合主张核对训练／调优／测试划分、跨项目或时间边界、重复样本与信息泄漏。只在相关时要求更广的覆盖。
- **评价判据与真实效果：** 检查测试、测试 oracle、静态分析、人工标注或其他判据能否衡量论文的目标。代码能运行、通过已有测试或获得更高文本相似度各有适用范围；将其对应到作者实际声称的正确性和工程收益，不直接等同于实际开发效果。
- **对照、归因与资源：** 检查相关 SE 方法及 LLM／agent baseline 的版本、输入信息、工具权限、采样次数、调参和预算是否合理。消融应检验核心设计的贡献；适用时结合时间、成本、人工投入和工作流约束解释结果。
- **统计与分析：** 根据数据设计检查随机性、效应大小、不确定性和统计方法，关注多个任务或同一项目内观测的相关性。定性或用户研究检查招募、标注、编码和分析过程。不机械要求每篇论文都有显著性检验或用户研究。
- **智能体／LLM 系统的工程问题：** 结合论文主张检查仓库上下文、环境与依赖、工具交互、状态管理、失败恢复、可靠性、测试、调试或安全边界。区分提出方案、在受控条件下验证和实际部署的证据。
- **有效性与可验证性：** 检查构念、内部、外部及结论有效性中真正影响结果解释的威胁，避免只复述作者的威胁列表。检查复现所需的配置、模型与提示、数据、脚本及依赖。区分查看材料和运行实验，不声称完成未执行的复现，也不把常规首轮审稿扩展成完整 artifact evaluation。
- **实际意义与表达：** 评价任务收益对开发者、维护者或软件系统的意义，以及关键方法和结果是否交代清楚。benchmark 提升需要结合其任务与评价范围解释；不要求每篇论文都具备工业部署或额外用户研究。

## 证据与问题严重程度

先识别评价属于哪种情况，再确定表述强度：

| 情况 | 审稿处理 |
| --- | --- |
| 技术缺陷 | 说明已核实的错误或无效设计，定位依据，并解释影响哪些结论。 |
| 证据不足 | 说明现有证据支持到什么程度，以及核心主张还缺哪项验证。 |
| 报告不清 | 指明缺失或含混的信息，解释其对理解、判断或复现的影响。 |
| 可选改进 | 作为次要建议提出，避免将拓展方向自动提升为接收条件。 |

“未报告”“材料未提供”“尚未检查”和“方法错误”分别处理。声称缺少某项内容前，检查提供的正文与相关附录，并在必要时说明检查范围。项目划分未说明时，可指出泛化判断尚缺依据；不能据此断定已发生数据泄漏。

关键意见应写清楚事实依据、对贡献或结论的影响，以及有针对性的澄清或验证请求。区分影响核心结论的问题、可澄清的问题和表达问题。评价优点与不足均以证据为准，不规定数量，不预设评分，不把通用的“工程意义不足”“实验不充分”作为完整理由。

## 必须应用的写作规范

起草任何审稿文字前，必须读取以下两份 skill；完成判断与证据核对后，将其规则用于中文稿与英文稿：

- [anti-defensive-writing](../anti-defensive-writing/SKILL.md)：直接提出观点，删除不增加事实或精度的缓冲、免责、自我削弱和反复限定。保留真实的不确定性、适用范围及影响技术判断的条件，用具体来源解释不确定性。
- [avoid-repetitive-contrast-style](../avoid-repetitive-contrast-style/SKILL.md)：减少重复的“不是……而是……”及英文对应句式，优先用事实、机制和因果关系解释判断；必要的技术区分可以保留。

将这些规则用于审稿人的表达，不修改被审论文。批评可以直接提出已核实的问题；科学上的否定结论与必要范围条件应保留。每项意见围绕一个主要问题，避免机械复述、空泛赞美和模型自述。写作检查保留在内部，不向模板追加修改日志或自检报告。
